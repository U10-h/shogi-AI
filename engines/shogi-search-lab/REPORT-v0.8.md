## 対象と判断の順序

対象は、これまで対戦していた **YaneuraOu NNUE KP256 6.03 / WASM 0.1.2** と自作v0.7です。最新版のやねうら王全体についての比較ではありません。[本家](https://github.com/yaneurao/YaneuraOu)と、[対戦相手の固定ソース](https://github.com/arashigaoka/YaneuraOu.wasm/tree/b2defb6d255ea44b3fead30e13f28b96e0ab0cc7)を区別しました。比較したソースは `vendor/yaneuraou/` に保存済みです。

従来の知見は次の三点でした。①駒得だけから手動38特徴へ変えると、3秒の着手比較と自己対局で改善した。②静的な教師評価との誤差を減らす学習が、探索後の手の改善につながるとは限らなかった。③手動評価を増やすと計算負荷も増えた。そこで今回は、**既存の学習済み評価を正確に再現し、評価・計算速度・探索の差を切り分ける**方針にしました。

NNUEの重みは対戦相手の配布物から借用しています。自分で学習した重み、独自のニューラルモデル、やねうら王を超える棋力を作ったという主張ではありません。従来の駒得・手動位置評価・学習実験も比較用として残しました。

## 実装したこと

- `src/nnue.{hpp,cpp}`：固定形式のNNUE読込・推論・差分更新。モデルヘッダ、構造、ブロックhash、末尾、切断、整数演算の上限を検査。非互換形式は明示的に拒否。
- `nnue-full`は全再計算、`nnue`は差分計算と同一局面の静的評価再利用、`nnue-verify`は差分accumulatorを毎回全再計算と比較。これらは同じ評価関数を計算する対照条件。
- 差分の基準は保存済みの盤面・持駒とaccumulator。親または同じ深さで前に評価した局面から変更分を計算する。静的評価の再利用なので、経路に依存する千日手判定や探索上下界とは分離。
- `src/advanced.cpp`：枝刈り等で使わない内部節点の評価と、王手中の静止探索で使わない評価を省略。評価を省いても王手回避手は従来どおり探索する。
- CLI/USIから評価を選択可能。NNUE内部値は本家の生値（歩90）を保持し、JSONには単位を明記。USIの通常評価表示は本家と同じく `score * 100 / 90` でcpへ変換。

持駒や駒番号を本家のルール実装に頼って直接評価するだけでは、互換実装の検証として不十分です。そのため別実行ファイル `nnue-oracle` を作り、本家の特徴変換器とネットワークを直接動かして照合しました。配布WASMは `eval` 命令に `Unknown command` を返したため、この方法を採っています。対局相手のWASM自体は交換していません。

## 実験条件

条件は `results/v0.8/protocol.json` に新規の着手比較前に保存しました。重みは固定で、この版で学習・重み調整はしていません。

- 正しさ：過去の実対局からの局面と、駒落ち相当・持駒を集中させた構成局面。本家の静的評価、差分と全再計算、探索結果、旧版の評価モード、入力エラー、USIの停止と評価切替を照合。
- 速度：従来の8局面、tactical・深さ3。NNUEの全／差分×評価の常時／必要時の4条件、手動評価の常時／必要時の2条件を各3回、順序を回して測定。同じ評価関数内で評価値・手・PV・ノード数の一致を必須とする。最初の計測は回帰テストと実行が重なったため破棄し、終了後に全条件を測り直した。
- 着手：従来と異なる4開始手順から固定教師・固定乱数で作った12局面。両版tactical、1手3000ms、反復深化、毎回新しい探索。比較相手の手動位置評価にもv0.8の不要計算省略を適用し、評価以外の探索条件をそろえる。教師の深さ12で、両版の選択手と教師の選択手の集合をMultiPV評価。
- 実対局：NNUE対手動位置評価は2開始手順×先後交換、双方300msで4局。NNUE対固定版やねうら王は1開始手順×先後交換、双方3000msで2局。定跡・ponder・入玉宣言なし。手数上限による未決着は勝ちにしない。

教師と改善版は同じNNUE重みを使います。したがって「教師との候補評価差」は探索を含む診断用の指標であり、独立した棋力の証明ではありません。過去の学習で見た局面かどうかは配布重みについて不明です。「新規12局面」は今回の比較用に新しく生成したという意味です。開始手順から8・16・24手進めた局面であり、終盤の網羅的評価ではありません。Native C++の自作とWASMの本家のNPSは実行基盤が異なるため、NPS差だけをアルゴリズム差とは解釈しません。

時間の数値は探索本体の `elapsed_ms` を使用し、プロセス起動やモデル読込は含めません。対局記録には呼び出し全体の `wallMs` も保存しています。NNUE用にProbCutなどの閾値を再校正していないため、今回はtactical以外の選択的設定の強さを推奨根拠にしていません。

今回組み合わせたのは、過去に検証したPVS・反復深化・履歴による並べ替え・静止探索と、固定NNUE・差分更新です。手動38特徴をNNUEへ単純加算すると、同じ駒得や玉の安全を重複評価する可能性があるため行っていません。NNUEは評価モードの選択肢として追加し、対照群の手動評価はそのまま残しています。

## 残る探索改善の優先順位

新規12局面のNNUE版では、探索した約404万ノードの **84.6%が静止探索**でした。TTによる即時打ち切りは7,298回、全ノードの約0.18%です（`search-counters.json`）。これは処理時間の割合ではありませんが、次に計測・改善する場所を絞る根拠になります。

1. **静止探索の手生成と並べ替え**：本家のMovePickerを参考に、必要な手を順に生成する。まずプロファイルで時間を測り、全合法手版と探索結果・PV・詰み判定が一致する範囲の変更を行う。
2. **保持情報の整理**：静的評価と並べ替え用の手は局面単位で保持できる。探索値を再利用するTTは、千日手の履歴と深さ条件の扱いを別に設計する。両者を一つの安全性判断で扱わない。
3. **選択的探索の再校正**：LMRやnull等は、同じ評価関数・同じ時間条件で、一機能ずつ対照比較する。NNUEに評価を変えただけで以前の閾値が最適になったとは仮定しない。

静的評価への教師誤差だけを再び最適化するよりも、同じ重みのまま探索効率と実対局を比較する方が、現状の差を切り分けやすいと判断しています。

終了ログと6局目の棋譜は完成していましたが、集計JSONの最後の状態欄がrunningのまま残りました。そのため `scripts/finalize_nnue_matches.mjs` で全6局・631着手・PV内3,157手を独立に再生し、終了局面、終了ログ、KIFを照合して状態欄を確定しました。指し手・評価値・時間は変更していません。照合結果と変更前後のhashは `results/v0.8/finalization-audit.json` に記録しています。

## 再現方法

```bash
make -j2
# v0.7比較用。保存済みソースを同じルール実装でコンパイルする
python scripts/build_checkpoint.py v0.7

# モデルと固定対戦相手を隣のディレクトリに取得する
python scripts/fetch_opponent.py "$PWD/../opponent"
export YANEURAOU_ASSETS="$PWD/../opponent"

make test
python scripts/build_nnue_oracle.py
python scripts/test_nnue.py
python scripts/test_nnue_usi.py

# 速度測定、着手比較、対局は順番に実行する
python scripts/benchmark_nnue.py
node scripts/benchmark_nnue.mjs
node scripts/match_nnue.mjs
python scripts/summarize_nnue.py

# 自分で使う場合（1手3秒）
./build/shogi-lab --advanced --preset tactical --eval nnue \
  --eval-model "$YANEURAOU_ASSETS/yaneuraou.data" \
  --depth 16 --iterative --time-ms 3000 --max-nodes 1000000000

# GUIから使うUSIモード
./build/shogi-lab --usi --preset tactical --eval nnue \
  --eval-model "$YANEURAOU_ASSETS/yaneuraou.data"
```

`--eval nnue-full` で差分計算を無効化、`--eager-eval` で不要な静的評価の省略を無効化できます。`--eval nnue-verify` は検証用で、速度比較には使いません。既定の評価モードは過去実験との互換性のためmaterialを維持します。

外部NNUEファイルは同梱していません。出典・固定hash・取得方法は `THIRD_PARTY.md` にあります。ソース、過去版checkpoint、各実験の条件と生データ、棋譜、再現スクリプトをZIPに含めています。時間制限の結果は実行環境の負荷で変化します。
