# Shogi Search Lab — 第1回：探索木を正しく小さくする

C++17 で探索と駒得評価を自作する、小さな将棋研究用エンジンです。
盤面更新・合法手生成は固定版の YaneuraOu を再利用します。
既存の将棋サイトとは別の実験コードです。

## まず実行する

Linux、g++ 13、GNU Make で動作確認しています。追加ダウンロードは不要です。

```bash
make -j2
make test
./build/shogi-lab --algorithm minimax --depth 3
./build/shogi-lab --algorithm alphabeta --depth 3
./build/shogi-lab --algorithm ordered --depth 3
```

同じ局面・同じ深さの結果を比較します。`score` は現在の手番側から見た評価値で、歩1枚を100点とします。
`depth 3` は先手・後手・先手のような **3手** で、双方が3手ずつ指す意味ではありません。
時間はミリ秒。`nodes` は根・末端を含む訪問回数で、重複局面も数えます。

入力例：

```bash
./build/shogi-lab --moves '7g7f 3c3d 2g2f 5c5d 2f2e 8b5b' --depth 3
./build/shogi-lab --sfen '4k4/9/P8/9/9/9/9/9/4K4 b - 1' --depth 3 --trace results/my-trace.jsonl
./build/shogi-lab --legal
./build/shogi-lab --perft 3
```

`--max-nodes` の既定値は200万。上限に達すると `complete:false`、`score:null`、終了コード3を返します。
途中の評価を完成した結果として扱わない設計です。現段階では持ち時間制御・USI対話プロトコルはありません。

## 自作と再利用の境界

| 部分 | 実装 |
|---|---|
| 盤面、利き、合法手、指す・戻す | YaneuraOu の固定ソース |
| 評価関数 | `src/evaluate.cpp`：盤上と持ち駒の単純合計 |
| 全幅探索・αβ探索・手の並べ替え | `src/search.cpp`：今回の自作 |
| 四回同一局面・連続王手の判定 | `src/board.cpp`：履歴を使う自作アダプター |
| 実験の実行・CSV集計 | `scripts/benchmark.py`：Python標準ライブラリのみ |
| 別ライブラリによる合法手照合 | `scripts/crosscheck.mjs`：任意、Node.js 18以上 |

YaneuraOu 本来の探索、学習済み評価関数、NNUE重みは使用しません。
上流の評価ソース1ファイルは盤面初期化に必要なダミー関数だけをコンパイルします。
合法手は `LEGAL_ALL` を使用し、任意の「不成」も比較対象に含めます。
出所と変更内容は [THIRD_PARTY.md](THIRD_PARTY.md) に記録しています。

## 今回の3条件

1. `minimax`：Negamax形式で、深さ内の全合法手を探索する基準。
2. `alphabeta`：同じ手順序で、αβの境界を使い結果に影響しない枝を省く。
3. `ordered`：駒取り・成りを先に読み、αβで省ける枝を増やす。

並べ替えの点数は探索結果の評価値には加えません。静かな手も残します。
取られる駒の盤上価値＋持ち駒価値、成りの価値上昇、動く駒の価値を使う単純な順序です。
駒の価値は研究開始時の手設定で、学習やパラメーター最適化はしていません。
同点の手が複数あると、探索順によって選ばれる手は異なります。

## 結果を読み、再実行する

[REPORT.md](REPORT.md) に測定結果と解釈をまとめています。

```bash
python3 scripts/benchmark.py
node scripts/crosscheck.mjs
python3 scripts/check_trace.py
# 任意：メモリ誤用・未定義動作の検査
bash scripts/sanitize.sh
```

ベンチマークは8局面×3方式×3回、各方式1回の予備実行後に順番を入れ替えて逐次測定します。
ソースハッシュ・環境・時刻は `results/environment.json`、全測定は `results/raw.json`、中央値は `results/benchmark.csv` にあります。
ベンチマーク中に別のCPU負荷をかけないでください。時間には共有環境の揺れがあります。
テスト済み深さでの全幅探索との一致は、対局の強さや局面評価の正しさを証明するものではありません。

## 探索木の記録

`results/promotion-trace.jsonl` は82局面の実例です。各行が一つのイベントです。

| イベント | 内容 |
|---|---|
| `enter` | 局面ID、親ID、指し手、深さ、α・β、SFEN |
| `return` | 評価値、`exact` / `lower` / `upper`、終了理由 |
| `cutoff` | 打切りを起こした手、境界、調べなかった兄弟の手 |
| `end` | 完了状態、省略されたログ件数 |

評価は各ノードの手番側から見た点です。`lower` は下限、`upper` は上限で、確定値ではありません。
`skipped_siblings` は直下で省いた手の数で、省いた子孫局面の総数ではありません。
ログ上限は既定2万イベント。省略されたログから完全な木を復元することはできません。
SFENだけでは過去の千日手履歴は復元できません。履歴が必要な追試には、元のSFENと `--moves` も保存してください。

## 現段階の範囲と次の実験

通常の合法手、詰み、四回同一局面、連続王手の反則を扱います。
入玉宣言・持将棋の裁定は未対応。SFENは形式・枚数・玉・非手番側への王手を検査しますが、過去から合法に到達できるかは証明しません。
探索は1スレッド、固定深さ。置換表、反復深化、静止探索、前向き枝刈り、自己対戦による棋力検証は未実装です。

次は「反復深化＋直前の最善手を優先」と「駒の取り返しまで読む静止探索」のどちらを先に研究するか決めます。
前者は時間内に深く読むため、後者は浅い探索の駒得評価を安定させるための候補です。
一つずつ導入し、変更前後の比較結果と、失敗した局面も残して進めます。
